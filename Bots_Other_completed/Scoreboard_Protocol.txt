BFA 8.3.7 (build 35662) battleground scoreboard protocol and client UI

Evidence boundary: the packet definitions/opcodes below come from the public 8.3.7-35662 TrinityCore-derived fork Lasko73/BFA_8.3.7-35662, not a retail client packet capture. The Lua behavior below is from EpsilonRP/BlizzardInterfaceCode830 (8.3.0 UI extraction); byte-for-byte identity of its Lua with build 35662 is unverified. Confirm the precise build's Interface/AddOns/Blizzard_PVPMatch and the actual server fork before relying on the listed UI gates. These sources DO verify what this particular 8.3.7 implementation writes and where a scoreboard-open failure may occur; they do not prove universal retail implementation details.

LUA / WINDOW GATES
QueueStatusFrame.lua's TogglePVPScoreboardOrResults first checks IsAddOnLoaded("Blizzard_PVPMatch"). It checks C_PvP.GetActiveMatchState(): Complete -> toggles PVPMatchResults:BeginShow(); otherwise, when Active AND NOT C_PvP.IsMatchConsideredArena(), it toggles PVPMatchScoreboard:BeginShow(). Inactive or pre-match state does not open a live battleground scoreboard. A currently active ARENA is explicitly excluded; its results can show after completion. The queue-status minimap button calls the toggle only when an active battlefield's showScoreboard gate allows it. QueueStatus_InActiveBattlefield checks GetBattlefieldStatus(i) == "active" and permits non-arena, completed arena (GetBattlefieldWinner()), or brawl; the dropdown has analogous arena restrictions. Sending stats alone does not set those gates.
PVPMatchScoreboard.lua: OnLoad registers PLAYER_ENTERING_WORLD and PVP_MATCH_ACTIVE; on an active match or entering with state Active, Init() registers PLAYER_LEAVING_WORLD, PVP_MATCH_COMPLETE, UPDATE_BATTLEFIELD_SCORE; PVP_MATCH_COMPLETE/leave shuts it and hides it. BeginShow() calls Init then ShowUIPanel. OnUpdate calls RequestBattlefieldScoreData() and PVPMatchUtil.UpdateTable(); UPDATE_BATTLEFIELD_SCORE repopulates from GetNumBattlefieldScores() and C_PvP.GetScoreInfo. Init uses C_PvP.IsMatchFactional(), GetBattlefieldArenaFaction(), ConstructPVPMatchTable() and, for faction tabs, C_PvP.GetTeamInfo(0) / (1) with .size. PVPMatchTable.lua uses C_PvP.GetScoreInfo as data provider, C_PvP.GetMatchPVPStatColumns() sorted by orderIndex with pvpStatID, and C_PvP.CanDisplayHonorableKills(), C_PvP.CanDisplayDeaths(), C_PvP.DoesMatchOutcomeAffectRating(). Team/rated display also queries C_PvP.IsRatedBattleground(), C_PvP.IsRatedArena() and C_PvP.GetTeamInfo. Thus even a window that opens can display zero rows if score data is absent or never updated.
PVPMatchResults.lua registers PLAYER_ENTERING_WORLD, PLAYER_LEAVING_WORLD, PVP_MATCH_ACTIVE; its active events include PVP_MATCH_COMPLETE and post-match item/currency reward updates. On PVP_MATCH_COMPLETE it auto-shows BeginShow() unless C_Commentator.IsSpectating(). Init reads C_PvP.GetActiveMatchWinner(), GetBattlefieldArenaFaction(), C_PvP.IsMatchFactional(), C_PvP.GetTeamInfo(0/1) for factional tabs, plus score/reward/rating functions such as C_PvP.GetScoreInfoByPlayerGuid(), C_PvP.GetPVPActiveMatchPersonalRatedInfo(), C_PvP.GetPostMatchItemRewards(), C_PvP.GetPostMatchCurrencyRewards() when relevant. Results require the client to enter Complete state with a winner, not merely a zero-score statistics response.

OPCODES IN THIS 35662 FORK (hex): CMSG_PVP_LOG_DATA 0x317C; SMSG_PVP_MATCH_STATISTICS 0x2931; SMSG_PVP_MATCH_INITIALIZE 0x294F; SMSG_PVP_MATCH_START 0x294D; SMSG_PVP_MATCH_COMPLETE 0x294E. All four server opcodes are marked CONNECTION_TYPE_INSTANCE by Opcodes.cpp. CMSG_PVP_LOG_DATA's Read() consumes NO payload. The fork registers its handler as STATUS_LOGGEDIN, PROCESS_THREADUNSAFE. It returns if the player has no Battleground; it ALSO explicitly returns for arenas on live request, noting that arena log data is sent at end instead. In a live non-arena battleground it builds and sends SMSG_PVP_MATCH_STATISTICS. Do not confuse the opcode for a message that this fork actually sends with a registered, but unimplemented, packet.

SMSG_PVP_MATCH_INITIALIZE serialization in this fork, in order: uint32 MapID; uint8 State; StartTime (Timestamp<>; serialized byte size depends on that wrapper, not independently verified); Duration (Duration<Seconds>; serialized byte size unverified); uint8 ArenaFaction; uint32 BattlemasterListID; one Registered bit; one AffectsRating bit; FlushBits. State enum InProgress=1, Complete=3, Inactive=4 in this class. On joining a match the Battleground.cpp sender maps STATUS_WAIT_JOIN / STATUS_IN_PROGRESS to InProgress, STATUS_WAIT_LEAVE to Complete; it sets map ID, local BG faction, list ID, and AffectsRating=isRated(), then sends initialize to the entering player. It does not necessarily mean the actual combat has started when WAIT_JOIN is serialized as InProgress. Exact Timestamp<> and Duration<Seconds> wire width must be checked in the fork's wrapper or capture: unverified here.
SMSG_PVP_MATCH_START: opcode 0x294D is present but Opcodes.cpp marks it STATUS_UNHANDLED and this fork's BattlegroundPackets.h/.cpp contains NO start packet class/writer; exact 35662 wire field layout, whether retail requires it and the trigger for sending it: unverified. Do NOT invent a payload or claim START is what unlocks the UI. Verify with an 8.3.7 capture if implementing retail fidelity.

SMSG_PVP_MATCH_STATISTICS serialization (PVPMatchStatisticsMessage::Write -> Data): first ONE bit RatingsPresent; then uint32 Statistics.size(); then 2 raw signed-int8 PlayerCount bytes in order [PVP_TEAM_HORDE, PVP_TEAM_ALLIANCE] (the Battleground.cpp builder explicitly indexes the counts that way; numeric team enum constants unverified); optional Ratings block if present, then exactly Statistics.size() player records. Ratings block: for index 0 and 1 in order, int32 Prematch[i], int32 Postmatch[i], int32 PrematchMMR[i]. IMPORTANT: top-level statistics array length is uint32, not a 6-bit count; PlayerCount is two separate 8-bit bytes and is NOT the record length. Follow the writer's bit-buffer packing/alignment at the bit/byte boundary; do not append a guessed padding byte.
Each player record, in order: ObjectGuid PlayerGUID (exact wire packing is determined by the fork's ObjectGuid serializer; unverified here); uint32 Kills; uint32 DamageDone; uint32 HealingDone; uint32 Stats.size(); int32 PrimaryTalentTree; int32 Sex; int32 Race; int32 Class; int32 CreatureID; int32 HonorLevel; for each stat, int32 PvpStatID THEN int32 PvpStatValue. Thus every battleground-specific stat is an ID/value PAIR, not merely one unlabelled value per slot. Then seven individual bits in order: Faction != 0; IsInWorld; HonorPresent; PreMatchRatingPresent; RatingChangePresent; PreMatchMMRPresent; MmrChangePresent; FlushBits. Conditional payloads in same order: if HonorPresent, uint32 HonorKills, uint32 Deaths, uint32 ContributionPoints; if PreMatchRatingPresent, uint32 rating; if RatingChangePresent, int32 change; if PreMatchMMRPresent, uint32 MMR; if MmrChangePresent, int32 change. The faction is a BIT inside each player record, not an independent byte. A live client must have player GUIDs, coherent team counts, faction bits and score data for useful rows; in-world player rows additionally get spec/sex/race/class/honor level from the current map if found. Whether a specific stat ID corresponds to a particular objective is battleground-specific and unverified here.

SMSG_PVP_MATCH_COMPLETE: uint8 Winner; Duration<Seconds> (exact byte width unverified); ONE bit LogDataPresent; FlushBits; if set, the entire PVPMatchStatistics structure serialized as above (including its counts, optional ratings and player records). At end Battleground.cpp sets the winner/duration, emplaces the LogData optional, fills it, serializes and sends the complete packet to all players still present. Late joiners to a completed battleground can also receive separate SMSG_PVP_MATCH_STATISTICS. LogData absent is legal per the optional wire field but would leave results without this embedded snapshot unless another stats packet has supplied it.

MINIMUM FLOW / FAILURE CHECKS
(1) Join accepted: send queue/active battleground status AND initialize with a coherent BG map, battlemaster-list ID, local faction and match state; client must load Blizzard_PVPMatch and have C_PvP.GetActiveMatchState()==Active and not consider the match an arena. This fork sends initialize on player add; a separate START payload is NOT verified in its code. (2) During an active non-arena BG, handle each CMSG_PVP_LOG_DATA issued by RequestBattlefieldScoreData() and reply with SMSG_PVP_MATCH_STATISTICS using the proper count, per-player records and faction bits; allow UPDATE_BATTLEFIELD_SCORE to refresh rows. Whether an unsolicited initial statistics message is necessary before the UI first opens: unverified; the Lua toggle gate depends on MATCH STATE, not GetNumBattlefieldScores()>0. (3) At completion, send SMSG_PVP_MATCH_COMPLETE with winner and embedded LogData so Complete/results show, including arena results; correct completion event/state transition must occur. Do not rely on a live arena CMSG handler response in this fork, since it deliberately skips arenas.
Known code-level mismatch patterns that can prevent an OPEN window: Blizzard_PVPMatch addon not loaded; match state never becomes Active or Complete (e.g. missing/wrong initialize or BG status); active match considered an arena; trying to toggle during pre-match/inactive; queue button/menu showScoreboard gate false; marking completion without updating client state/event. Patterns that can yield an OPEN BUT EMPTY/BROKEN window: dropping the live CMSG request; sending only end-match data during a running match; constructing stats as bare values rather than int32 ID/value pairs; writing the faction as byte rather than bit; wrong team count order or count/array-length mismatch; misordered optional flags/fields or GUID serialization; non-factional match with incorrectly assumed faction tabs/team info. These are consequences of the verified Lua/writer logic, NOT a verified list of actual emulator bug reports. Whether the particular private core has each bug: unverified.
