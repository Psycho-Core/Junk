1. THE SHORT ANSWER
===================

Each of the three answers contradicts at least one common assumption, so the short answer comes
first.

  - The rear arc is 180 degrees wide. TrinityCore tests it as target->HasInArc(pi, attacker):
    the attacker must be outside the target's forward half-plane, i.e. more than 90 degrees off
    the target's nose. It is a half-plane, not a narrow cone behind the tail.
  - None of Backstab, Shadowstrike, Ambush, Mangle or Shred requires the rear arc in 8.3.7.
    Patch 6.0.2 removed the facing requirement from Backstab, Ambush, Shred and Mangle, and
    Shadowstrike teleports the rogue behind the target instead of demanding that it stand there.
    Only Backstab still pays for position: 20% more damage from behind.
  - The arc still matters, for two mechanical reasons: attacks from the rear cannot be parried
    or blocked (and, against players, cannot be dodged), and Backstab's bonus is computed with
    the same 180 degree test.
  - A creature turns to face the character it is chasing (ChaseMovementGenerator calls
    SetInFront on its target), so the arc is a moving target whenever the tank moves, a taunt
    swaps, or the companion itself is the mob's victim.
  - A talent build in 8.3.7 is exactly 21 choices: 7 rows (TierID 0-6) x 3 columns (ColumnIndex
    0-2), one talent per row. Talent.db2 holds 648 rows for the 36 player specializations in
    build 35662.
  - The row is stored on the talent, not on the character: a talent row's SpecID, ClassID,
    TierID and ColumnIndex decide which specialization may take it in which slot. Rows with
    SpecID 0 are class-wide fallbacks that a specialization-specific row overrides.
  - The client sends Talent.db2 row ids, not spell ids: CMSG_LEARN_TALENTS carries a list of
    Talent IDs, and the server stores them per specialization group in the
    characters.character_talent table as (guid, talentId, talentGroup).
  - 8.3.7 has no talent export string and no loadout code. That feature belongs to the
    Dragonflight talent system (10.x), where loadouts are TraitConfig objects; a BfA character
    has nothing to export except the 21 row/column pairs or the 21 talent ids.
  - Talent validation is a fixed list of checks in Player::LearnTalent: combat, death, no
    specialization, unknown id, wrong specialization, wrong class, row not unlocked, wrong
    talent for the slot, not in a rest area, talent on cooldown, already known.
  - Skinning required skill is a pure function of the creature's level; for levels 1-73 it is 1,
    (level-10)*10 or level*5, and the server code extends it in bands up to 900.
  - Herbs and ores are the opposite: their requirement comes from the node, not from a formula.
    Every classic, Outland, Northrend, Cataclysm and Pandaria node has a fixed
    orange/yellow/green/grey band, tabulated in section 4.4 and 4.5.
  - From Legion onward the per-node bands collapse: BfA herbs and ores need only rank 1 of the
    Battle for Azeroth skill line and grey out at 150-175. The requirement is the expansion's
    skill line, not the old 1-300 scale.
  - Gathering skill rises on the colour of the node or corpse: orange 100%, yellow 75%, green
    25%, grey 0% (TrinityCore defaults), one point per success, with elites doubling a skinning
    chance and a node skilling up a given character only once per respawn.

2. POSITIONING: THE REAR ARC
============================


2.1  The geometry the server tests
----------------------------------
One test decides everything. It is made on the server at cast time, from the target's
orientation and the two units' positions at that instant:

  - TrinityCore's Spell::CheckCast returns SPELL_FAILED_NOT_BEHIND when the spell carries the
    custom attribute SPELL_ATTR0_CU_REQ_CASTER_BEHIND_TARGET and target->HasInArc(pi, caster) is
    true.
  - Position::HasInArc(arc, obj, border) treats its second numeric argument as a divisor of the
    arc: the accepted half-angle is arc / border, and border defaults to 2.0. With arc = pi the
    window is +/- 90 degrees.
  - WorldObject::isInBack(target, arc) is !HasInArc(2*pi - arc, target), which with the usual
    arc = pi is the same rear half-plane. Scripts that want a narrower cone pass a smaller arc
    to isInBack.

| Angle from the target's nose | In the front arc?  | Behind? |
|------------------------------|--------------------|---------|
| 0-90 degrees                 | yes                | no      |
| 90-180 degrees               | yes, at 90 exactly | yes     |

So the rear arc is 180 degrees wide - 90 degrees either side of the target's back - and a
character standing level with the target's shoulder is already behind it. Anything the companion
does with position can be reduced to one number: the absolute angle between the target's
orientation and the bearing from the target to the companion.

The same constant is used by the hit-result code (section 2.3), which is why the practical
meaning of the arc survived the removal of the abilities' positional requirements.


2.2  The five abilities, one by one
-----------------------------------

| Ability      | Spell id | Spec     | Behind needed | Arc effect       |
|--------------|----------|----------|---------------|------------------|
| Backstab     | 53       | Subtlety | no            | +20% damage      |
| Ambush       | 8676     | Outlaw   | no            | none             |
| Shadowstrike | 185438   | Subtlety | no            | teleports behind |
| Mangle       | 33917    | Guardian | no            | none             |
| Shred        | 5221     | Feral    | no            | none             |

Patch 6.0.2 is the reason. Its notes say, ability by ability: Backstab "can now be used on
either side of the target, in addition to behind the target"; Ambush "No longer requires the
rogue to be behind the target"; Shred "No longer has behind enemy position requirement"; Mangle
was redesigned into a bear-form only ability in the same patch. The 2020 revisions of the five
ability articles repeat those changes.

What each ability does require is worth writing down, because a companion that checks the wrong
thing will refuse valid casts:


| Ability      | Real requirement in 8.3.7          | Id     |
|--------------|------------------------------------|--------|
| Backstab     | dagger in the main hand; 35 energy | 53     |
| Ambush       | stealth; melee weapon; 60 energy   | 8676   |
| Shadowstrike | stealth for the teleport; daggers  | 185438 |
| Mangle       | bear form only (Guardian)          | 33917  |
| Shred        | cat form only (Feral); 40 energy   | 5221   |

Backstab's bonus is the only positional effect left among the five. It was set to 20% in patch
7.2.5 (previously 30%) and is described in the 2020 article revision. The server computes it
with the same HasInArc(pi) test, so the practical rule for a companion is: stand behind only if
the cast is Backstab.

Which specializations need the arc, then: of the five abilities, only Subtlety's Backstab gains
anything from it. Feral (Shred), Guardian (Mangle), Outlaw (Ambush) and Assassination (which has
none of the five) have no positional component in 8.3.7. Every melee specialization still wants
the rear arc for the parry and block reason in 2.3, and that includes a tank that is attacking a
mob which is not currently attacking it.


2.3  What the arc actually buys: parry, block, dodge
----------------------------------------------------
TrinityCore's melee result function removes defensive outcomes when the attacker is not in the
victim's forward arc. This is the real reason melee characters stand behind a boss.


| Attack direction  | Parry    | Block    | Dodge, player victim | Dodge, creature victim |
|-------------------|----------|----------|----------------------|------------------------|
| Front 180 degrees | possible | possible | possible             | possible               |
| Rear 180 degrees  | never    | never    | never                | still possible         |

  - Unit::MeleeSpellHitResult clears canParry and canBlock when !victim->HasInArc(pi, attacker)
    and the victim has no SPELL_AURA_IGNORE_HIT_DIRECTION.
  - Against a player victim it also clears canDodge; creatures keep their dodge chance from
    behind, which is why a rear attack is not a guaranteed hit.
  - Ranged attacks cannot be dodged or parried at all; block still applies, and deflect is
    rolled only when the attacker is inside the victim's front arc, so ranged attacks are
    directional in two ways instead of four.

2.4  What to do when the target turns
-------------------------------------
A target's orientation is server state, and three things change it:

  - Movement. A creature chasing a victim turns to face it: ChaseMovementGenerator::Update calls
    owner->SetInFront(target) every update, so a mob always ends up facing the character that
    has aggro, not the one that is behind it.
  - Casting. A creature that begins a cast faces its spell target, and then either keeps facing
    it for the cast (the SPELL_ATTR5_AI_DOESNT_FACE_TARGET case, which freezes turning and sets
    UNIT_STATE_FOCUSING) or is free to turn.
  - Scripts and abilities. SmartScript actions and scripted encounters can set facing directly,
    and CannotTurn() prevents a creature from turning at all.
Two consequences follow for a companion:

  - If somebody else holds aggro, the target faces that character and the rear arc sits opposite
    them. The bigger the group, the more the tank's position defines where "behind" is - the
    companion should compute it, not memorise a spot.
  - If the companion itself holds aggro, the rear arc is unreachable while it keeps aggro: the
    mob faces whoever it is chasing. Either the companion tanks and gives up Backstab's bonus,
    or it drops aggro before switching to rear-arc attacks.

2.5  Companion positioning procedure
------------------------------------
   1. Read the target's orientation and both positions. Compute the bearing from the target to
      the companion, subtract the target's orientation, normalise to -180..180 and take the
      absolute value: that is the off-nose angle.
   2. Treat anything over 90 degrees as behind. Aim for 100-120 degrees, not 91: the check uses
      the positions at the instant the server processes the cast, which is one latency tick
      after the client decided it was in position.
   3. Move along the circle at melee range rather than through the target. Cutting through the
      target crosses the front arc and gives a window in which the cast fails.
   4. Re-check immediately before every cast that needs the arc; do not cache a "behind" flag
      across a target re-face.
   5. For a target that turns continuously (a kiting mob, a boss rotating to a new tank), hold a
      fixed offset of about 120 degrees and orbit it rather than chasing the exact rear point.
   6. Never let the rule block a cast. In 8.3.7 no spell the companion casts should fail with
      SPELL_FAILED_NOT_BEHIND (81) for position; if a server does return it, that server's spell
      data carries the behind attribute and the position has to be fixed before the next
      attempt.

2.6  What has no id
-------------------
  - No map, coordinate, creature or item id belongs to this rule. The arc is a constant (pi),
    and the angle is recomputed from live positions every time.
  - The only id in the whole mechanic is the error code: SPELL_FAILED_NOT_BEHIND = 81. Two
    related codes exist and are often confused: SPELL_FAILED_UNIT_NOT_BEHIND = 156 (the target
    is not behind something) and ERR_PET_SPELL_NOT_BEHIND = 433.
  - The custom spell attribute SPELL_ATTR0_CU_REQ_CASTER_BEHIND_TARGET has no client-facing id
    in build 35662; which spells carry it is server data (spell_custom_attr), not client data.
    Whether the 8.3.7 client encodes a behind requirement at all is UNVERIFIED.

3. TALENT LOADOUTS
==================


3.1  The shape of a build
-------------------------
A Battle for Azeroth specialization has seven talent rows and three talents in each row. A
finished build is therefore 21 choices, one per row, and the choice in each row is a column
index 0, 1 or 2. There are no talent points, no partial ranks and no cross-row prerequisites in
this system - the only precondition for a row is the character's level.


| Quantity                    | Value in build 35662 | Where it comes from   |
|-----------------------------|----------------------|-----------------------|
| Rows per specialization     | 7 (TierID 0-6)       | Talent.db2            |
| Columns per row             | 3 (ColumnIndex 0-2)  | Talent.db2            |
| Choices in a finished build | 21                   | one per row           |
| Talent rows in Talent.db2   | 648                  | client data           |
| Player specializations      | 36                   | ChrSpecialization.db2 |
| Rows with SpecID 0          | 79                   | class-wide fallbacks  |


3.2  How a row and column are stored
------------------------------------
The talent is the record; the character only records which talents it has taken. Every row of
Talent.db2 carries its own row, column, class and specialization:


| Field            | Meaning                                                            |
|------------------|--------------------------------------------------------------------|
| ID               | the talent id; this is what the client sends and the server stores |
| SpellID          | the spell the talent grants or applies                             |
| OverridesSpellID | the spell this talent replaces, or 0                               |
| SpecID           | ChrSpecialization id, or 0 for a class-wide row                    |
| ClassID          | 1-12, the class that owns the row                                  |
| TierID           | the row, 0-6                                                       |
| ColumnIndex      | the column inside the row, 0-2                                     |
| Flags            | 0 on all 648 rows of build 35662                                   |
| CategoryMask_0/1 | category masks; 0 on all 648 rows in this build                    |
| Description_lang | empty on 647 of the 648 rows in this build                         |

Resolution rule, and the one thing an implementer usually gets wrong: a slot (class,
specialization, row, column) can be occupied by a specialization-specific row and by a
class-wide row at the same time. The specialization-specific row wins. Rows with SpecID 0 exist
because Blizzard stored some choices once for the whole class and overrode them only for the
specializations that differ.

  - Tested against the CSV: for each of the 36 specializations, taking the spec-specific row
    first and falling back to the SpecID 0 row, every specialization resolves to exactly 21
    slots with no slot filled twice.
  - The 79 SpecID 0 rows are not extra talents; they are the default occupant of a slot that
    some specializations replace.
  - A talent's ClassID must match the character's class even when SpecID is 0 - the class-wide
    row belongs to one class, not to all of them.

3.3  Which rows are unlocked at which level
-------------------------------------------
The client ships the answer as a table indexed by level, NumTalentsAtLevel.db2, with separate
columns for death knights and demon hunters. TrinityCore reads exactly this table
(DB2Manager::GetNumTalentsAtLevel) and puts the result into the player's MaxTalentTiers field.
Rows unlock at:


| Level   | Rows, normal classes | Rows, death knight | Rows, demon hunter |
|---------|----------------------|--------------------|--------------------|
| 1-14    | 0                    | 0                  | 0                  |
| 15      | 1                    | 0                  | 0                  |
| 30      | 2                    | 0                  | 0                  |
| 45      | 3                    | 0                  | 0                  |
| 56      | 3                    | 1                  | 0                  |
| 57      | 3                    | 2                  | 0                  |
| 58      | 3                    | 3                  | 0                  |
| 60      | 4                    | 4                  | 0                  |
| 75      | 5                    | 5                  | 0                  |
| 90      | 6                    | 6                  | 0                  |
| 99      | 6                    | 6                  | 1                  |
| 100     | 7                    | 7                  | 2                  |
| 102     | 7                    | 7                  | 3                  |
| 104     | 7                    | 7                  | 4                  |
| 106     | 7                    | 7                  | 5                  |
| 108     | 7                    | 7                  | 6                  |
| 110-120 | 7                    | 7                  | 7                  |

Two notes. The table is monotonic and costs nothing to compute: the row count only ever goes up.
And the 2020 Talent article lists death knight rows as unlocking at 56, 57, 58, 60, 75 and 90 -
six levels for seven rows; the client table above gives the seventh row at 100, which is what
the server uses.

The example shows both storage styles in one specialization: row 2 is entirely inherited, rows 1

every id in a slot belongs to the spec, picks the wrong id on the eight inherited slots.


3.5  How the choice is sent and stored
--------------------------------------
  - The client sends CMSG_LEARN_TALENTS with a list of Talent.db2 ids (uint16 each). The count
    is a 6-bit field in TrinityCore's reader, and the array is sized to 7 entries - one per row.
  - The server answers SMSG_LEARN_TALENT_FAILED when any id in the batch is refused, carrying
    the reason, the spell id and the refused talent ids. Success is silent apart from a talent
    info update.
  - The server stores the ids per specialization group in characters.character_talent, as (guid,
    talentId, talentGroup). talentGroup is the specialization slot 0-4 (MAX_SPECIALIZATIONS =
    5), so one character can hold a different 21 ids for each of its specializations.
  - On login the server runs SELECT talentId, talentGroup FROM character_talent WHERE guid = ?
    and re-applies each row; saving deletes and re-inserts the whole table for the character.
  - Nothing in the database records a row or a column. Row and column live on the Talent.db2 row
    that the stored id points at, which is why a client DB2 change can silently move a stored
    talent.

3.6  How a selection is validated
---------------------------------
TrinityCore's Player::LearnTalent performs the checks in this order and returns the first
failure. It is the specification a companion should mirror, because it is what the server will
answer with:


| #  | Check                                          | Failure code                 |
|----|------------------------------------------------|------------------------------|
| 1  | the character is not in combat                 | AFFECTING_COMBAT (5)         |
| 2  | the character is alive                         | CANT_DO_THAT_RIGHT_NOW (4)   |
| 3  | a primary specialization is chosen             | NO_PRIMARY_TREE_SELECTED (3) |
| 4  | the talent id exists in Talent.db2             | UNKNOWN (1)                  |
| 5  | SpecID is 0 or equals the player's spec        | UNKNOWN (1)                  |
| 6  | ClassID equals the player's class              | UNKNOWN (1)                  |
| 7  | TierID is below MaxTalentTiers for the level   | UNKNOWN (1)                  |
| 8  | the id is the best match for its slot          | UNKNOWN (1)                  |
| 9  | a rest area, or the allow-change flag          | REST_AREA (8)                |
| 10 | the removed talent's spell is not on cooldown  | CANT_REMOVE_TALENT (6)       |
| 11 | the row has a non-zero SpellID                 | UNKNOWN (1)                  |
| 12 | the talent and its spell are not already known | UNKNOWN (1)                  |

Check 8 is the subtle one: the server walks every talent in the same (class, row, column),
prefers the specialization-specific row over the class-wide one and refuses anything that is not
that best match. A companion that sends the class-wide id for a slot that the specialization
overrides is refused with TALENT_FAILED_UNKNOWN - the same code as a nonexistent id, which is
why the failure is hard to diagnose.


| Value | Result                                           |
|-------|--------------------------------------------------|
| 0     | TALENT_LEARN_OK                                  |
| 1     | TALENT_FAILED_UNKNOWN                            |
| 2     | TALENT_FAILED_NOT_ENOUGH_TALENTS_IN_PRIMARY_TREE |
| 3     | TALENT_FAILED_NO_PRIMARY_TREE_SELECTED           |
| 4     | TALENT_FAILED_CANT_DO_THAT_RIGHT_NOW             |
| 5     | TALENT_FAILED_AFFECTING_COMBAT                   |
| 6     | TALENT_FAILED_CANT_REMOVE_TALENT                 |
| 7     | TALENT_FAILED_CANT_DO_THAT_CHALLENGE_MODE_ACTIVE |
| 8     | TALENT_FAILED_REST_AREA                          |
| 9     | TALENT_FAILED_UNSPENT_TALENT_POINTS              |
| 10    | TALENT_FAILED_IN_PVP_MATCH                       |

Three of these need translating for a companion author: TALENT_FAILED_UNKNOWN covers every id,
class, spec and slot problem and is the answer to almost every mistake;
TALENT_FAILED_CANT_REMOVE_TALENT means the talent being replaced still has its spell on
cooldown; and values 2 and 9 are leftovers from the pre-Mists talent trees - Player::LearnTalent
never returns either of them.


3.7  Is there an export string or loadout code in 8.3.7?
--------------------------------------------------------
No. Three separate facts point the same way:

  - The 2020 revision of the Talent article - the BfA-era text - describes only rows, levels,
    rest-area rules and the Tome of the Clear Mind items. It documents no export or import
    format, and no loadout system at all.
  - The loadout system that a modern player thinks of (saved builds with names, and a string
    that can be pasted into another character) belongs to the Dragonflight talent system. The
    Dragonflight article describes loadouts as TraitConfig objects switched through
    C_ClassTalents and the /loadoutname command, which belong to that expansion and have no
    counterpart in any 8.3.7 source read.
  - Nothing in the 8.3.7 talent data is a serialised blob: Talent.db2 rows, ChrSpecialization
    rows and the character_talent table are the whole model. A build is 21 small integers.
What a companion should use instead, in order of preference:


| Representation         | Size     | Stable?                           |
|------------------------|----------|-----------------------------------|
| 21 (row, column) pairs | 21 bytes | yes, while the spec keeps 7 x 3   |
| 21 Talent.db2 ids      | 42 bytes | one client build only             |
| 21 spell ids           | 84 bytes | yes, if the spell does not change |

Third-party talent calculators publish their own encodings (Wowhead's calculator URLs are the
best known). Those are properties of the web site, not of the client, and none of them is
accepted by an 8.3.7 client - there is no import box to paste one into.


3.8  Companion validation procedure
-----------------------------------
   1. Resolve the intended build to 21 (row, column) pairs for the companion's current
      specialization, using the spec-specific row first and the SpecID 0 row as the fallback.
   2. Compare the resulting ids with what the character already has; send only the differences,
      and at most one id per row.
   3. Check the level gate before sending: row N needs the NumTalentsAtLevel value for the
      character's level to be at least N+1 (client table, section 3.3).
   4. Check that the character is in a rest area or carries the allow-talents-change flag, and
      that it is alive and out of combat.
   5. Do not send a batch containing two talents from the same row: the second one is a
      replacement of the first, which triggers the rest-area and cooldown checks again.
   6. Read the SMSG_LEARN_TALENT_FAILED reason before retrying; TALENT_FAILED_UNKNOWN is
      ambiguous by design and usually means the slot resolution in step 1 was wrong.

4. GATHERING SKILLS: SKINNING, HERBALISM, MINING
================================================


4.1  The skills and their ids
-----------------------------

| Profession | Skill line | Trainer spell | BfA skill line | BfA name                        |
|------------|------------|---------------|----------------|---------------------------------|
| Skinning   | 393        | 8613          | 2557           | Kul Tiran / Zandalari Skinning  |
| Herbalism  | 182        | 2366          | 2549           | Kul Tiran / Zandalari Herbalism |
| Mining     | 186        | 2575          | 2565           | Kul Tiran / Zandalari Mining    |

Each expansion has its own child skill line under the base profession, distinguished by
ParentTierIndex (4 = Classic and one more per expansion, 11 = Battle for Azeroth). TrinityCore
resolves the child line from the creature's ContentTuning expansion id
(Player::GetProfessionSkillForExp), which is why a level 120 corpse is skinned against the BfA
skill line and not against the 1-300 Classic one.

  - Find Herbs is spell 2383, Find Minerals is spell 2580, Skinning has no tracking spell.
  - The base skill lines carry no maximum of their own in the client; the cap belongs to the
    rank the character has learned (BfA ranks cap at 150-175, see 4.6).

4.2  Skinning: the required skill is a function of creature level
-----------------------------------------------------------------
Skinning is the one gathering profession whose requirement is not a per-node value: it is a
function of the creature's level. TrinityCore computes it in Spell::EffectSkinning with the
bands below, which reproduce the classic 1-73 rule the 2020 Skinning article states and extend
it for later content.


| Creature level | Required skill    | Examples                        |
|----------------|-------------------|---------------------------------|
| 1-10           | 1                 | 1 -> 1, 10 -> 1                 |
| 11-19          | (level - 10) x 10 | 11 -> 10, 19 -> 90              |
| 20-73          | level x 5         | 20 -> 100, 60 -> 300, 73 -> 365 |
| 74-79          | level x 10 - 365  | 74 -> 375, 79 -> 425            |
| 80-84          | level x 5 + 35    | 80 -> 435, 84 -> 455            |
| 85-87          | level x 15 - 805  | 85 -> 470, 87 -> 500            |
| 88-92          | (level - 62) x 20 | 88 -> 520, 92 -> 600            |
| 93-104         | level x 5 + 175   | 93 -> 640, 104 -> 695           |
| 105-107        | level x 15 - 905  | 105 -> 670, 107 -> 700          |
| 108-112        | (level - 72) x 20 | 108 -> 720, 112 -> 800          |
| 113-122        | (level - 32) x 10 | 113 -> 810, 120 -> 880          |
| 123 and up     | 900               | flat cap                        |

Read the table literally: the bands are not monotonic. Level 104 requires 695 and level 105
requires 670, because the two bands were fitted at different times. A companion should use the
formula, not an interpolation between rows.

The classic part of this table (levels 1-73) matches the 2020 Skinning article's wording: "1 for
level 1-10 mobs; (10 times mob level) minus 100 for level 11-20 mobs; 5 times level for level
21-73 mobs". The article's own 74-87 numbers differ from the code (it gives 470 at level 84 and
530 at level 87, where the code gives 455 and 500); the code is what the server computes and is
treated as authoritative here.

Two cautions before using this for a BfA companion:

  - TrinityCore uses this value only to pick the skill-up band. EffectSkinning does not refuse
    the cast when the player's skill is too low - it fills the skinning loot and then rolls the
    skill-up. On a stock server the "Requires Skinning (X)" refusal is a client-side check.
    Whether an 8.3.7 fork enforces it server-side is UNVERIFIED.
  - The value is expressed against the base skill (1-300 style). BfA corpses are skinned against
    the BfA skill line, whose cap is 150-175, so the level 108-122 rows of the table cannot be
    the number a BfA character sees. The exact conversion to the BfA scale is UNVERIFIED; what
    is verified is that BfA content is gated on the BfA skill line, not on the base one.

4.6  How the skill rises
------------------------
Gathering uses one shared routine (Player::UpdateGatherSkill) for all three professions, and the
colour of the node or corpse selects the chance:


| Colour | Node state    | Chance | TrinityCore setting      |
|--------|---------------|--------|--------------------------|
| Red    | skill too low | n/a    | -                        |
| Orange | red + 0       | 100%   | SkillChance.Orange = 100 |
| Yellow | red + 30      | 75%    | SkillChance.Yellow = 75  |
| Green  | red + 60      | 25%    | SkillChance.Green = 25   |
| Grey   | red + 90      | 0%     | SkillChance.Grey = 0     |

  - The bands are computed, not stored: red = the node's or corpse's required skill, yellow =
    red + 30, green = yellow + 30, grey = green + 30. GameObject templates can override yellow
    and grey through their trivial-skill low/high fields, in which case green is the midpoint.
  - One point per success (SkillGain.Gathering = 1). Skinning doubles the chance against elite
    creatures; the multiplier is 2 for elites and 1 otherwise.
  - A node gives a given character at most one skill-up until it respawns. TrinityCore keeps a
    per-node skill-up list keyed by player GUID, which is why a party cannot farm one vein.
  - Mining and skinning also decay: SkillChance.MiningSteps and SkillChance.SkinningSteps
    right-shift the chance by skill / steps, which halves it once per steps skill points.
    Setting either to 0 disables the decay.
  - Smelting gives Mining skill points as well, and fishing has its own counter, so a companion
    cannot infer profession skill from gathered node count alone.
  - The cap is the rank's, not the profession's: a BfA rank caps at 150 for Mining and Skinning
    and 175 for Herbalism according to the 2020 proficiency tables. TrinityCore refuses to raise
    a skill once its value reaches the rank maximum, so no amount of gathering pushes a
    companion past the cap.

4.7  What has no id
-------------------
  - Node coordinates and spawn points are server data (the gameobject table and its pool
    templates). They do not exist in client DB2 and cannot be verified from build 35662.
  - The herb and ore node objects themselves are gameobject_template entries in the server
    database; the client ids in the tables above are the item ids of what they yield, not the
    node ids.
  - Per-creature skinning loot is skinning_loot_template keyed by creature entry, again server
    data. The creature entries that carry it are not part of the client build.
  - Skill-up chances are server configuration, not client constants: the percentages in 4.6 are
    TrinityCore's defaults (SkillChance.* in worldserver.conf.dist), and a private server can
    set them to anything.

5. UNVERIFIED
=============

Everything below either could not be read from client data or the server source, or is a point
where two sources disagree and neither can be preferred:

  - Whether the 8.3.7 client encodes the behind-target requirement at all. The server attribute
    that enforces it (SPELL_ATTR0_CU_REQ_CASTER_BEHIND_TARGET) is server data, and no client
    column in build 35662 was found that carries the same bit.
  - Whether an 8.3.7 server refuses a skinning cast when the character's skill is below the
    creature's requirement. TrinityCore master does not; it trusts the client to have shown the
    refusal.
  - The conversion of the level-based skinning requirement (section 4.2) onto the 150-175 point
    Battle for Azeroth skill line. The formula is verified; the scale it is compared against for
    BfA corpses is not.
  - The skill at which a level 110-120 BfA corpse becomes skinnable. No 2020 wiki table records
    it and the client does not ship a per-level requirement table for skinning.
  - The item ids behind three special herb nodes - Blacker Lotus, Frozen Herb and Sha-Touched
    Herb. Their article rows list no yield and ItemSparse has no item under those names; the
    nodes are not ordinary herb nodes.
  - The green and grey thresholds of Truesilver Deposit and Dark Iron Vein. The 2020 Mining
    article leaves both empty, marked "?" in section 4.5.
  - The exact BfA rank caps. The 2020 proficiency tables give Herbalism 1-175, Mining 1-150 and
    Skinning 1-150, and the Zin'anthid row greys at 175, so the three do not agree with each
    other; only the grey values in sections 4.4 and 4.5 are sourced.
  - Whether a TrinityCore 8.3.7 fork stores talents under the same talentGroup indexing (0-4)
    and the same characters.character_talent columns. The code quoted is the master branch; no
    8.3.7 branch exists.
  - The client build in which talent import and export strings first appeared. The feature is
    documented for the Dragonflight talent system, which puts it after 8.3.7; the exact patch is
    not stated in the sources read.
  - Which creature entries drop which skinning material on a given realm. That is
    skinning_loot_template, server data, not client data.
  - The per-node spawn coordinates and node object ids for every herb and ore. These are
    gameobject_template rows in the server database.
  - Whether the 60-degree or other narrower arcs appear anywhere in 8.3.7 spell data. The
    server's own tests all use pi (180 degrees); narrower cones would require a spell script,
    and none was found in the source read.
